# Стандарт кодування SportEvents

**Дисципліна:** Конструювання програмного забезпечення. **Варіант:** 20.
**Область:** SportEvents.Core, SportEvents.Console, SportEvents.Tests, labs.
**Основа правил:** .editorconfig і Directory.Build.props, C# 12 / .NET 8.
**Статус:** навчальний стандарт, який можна перевірити командою `dotnet format SportEvents.sln --verify-no-changes`.

## 1. Загальні правила

1. Один вихідний файл зберігається у UTF-8 і завершується новим рядком. Пробіли наприкінці рядка видаляються.
2. Відступ — чотири пробіли; фігурні дужки C# пишемо на новому рядку.
3. Файли класів розміщуємо у просторі назв, що відповідає ролі: `SportEvents.Core.Domain`, `SportEvents.Core.Application`, `SportEvents.Core.Infrastructure`.
4. Модуль Core не має виконувати `Console.ReadLine` або `Console.WriteLine` для доменної логіки. Розбір рядків користувача — в Console, Core приймає типізовані значення.
5. Публічні методи документуються XML-коментарями, що пояснюють правила, а не дублюють назву методу.
6. Доменні константи називаються за змістом. Магічні числа з предметної області не залишаються в обчисленнях без пояснення.
7. Після кожної серії змін запускаємо `dotnet build SportEvents.sln -c Release -warnaserror` і xUnit-тести; перед PR — `dotnet format --verify-no-changes`.

## 2. Іменування

| Елемент | Правило | Приклад із предметної області |
|---|---|---|
| Клас / record / enum | PascalCase | `SportsEvent`, `Participant`, `EventStatus` |
| Інтерфейс | Префікс I, далі PascalCase | `IEventRepository`, `IClock` |
| Метод / властивість | PascalCase, назва дії | `CreateEvent`, `AddParticipant` |
| Локальна змінна / аргумент | camelCase | `eventId`, `birthDate` |
| Приватне поле | Обраний стиль проєкту, послідовність важливіша за змішування | `repository`, `clock` у `EventService` |
| Булева перевірка | Is / Has / Can | `IsValidRaceDuration` |
| Метод зі спробою | Try + дія, повертає результат успіху | `TryParse` на межі вводу |
| Асинхронний метод | Суфікс Async | `SaveAsync` при появі async-сховища |
| xUnit тест | Метод_Умова_Очікування | `Format_Negative_Throws` |

У навчальних лабораторних надано чужий погано оформлений код; його транлітеровані й короткі назви допускаються **тільки як історичний стан «до»**, а не як стандарт для нового коду.

## 3. Типи, інваріанти та помилки

* Час результату — `TimeSpan`, а не `double` чи довільний текст.
* Дата народження — `DateOnly`; подія переходить між станами `EventStatus` через методи сервісу.
* Нульовий або від’ємний час фінішу неприпустимий, перевірка є у `RaceTimeFormatter`.
* На неправильні аргументи відповідаємо `ArgumentException`/`ArgumentOutOfRangeException`; на порушення бізнес-правила — `DomainRuleException`.
* Помилки збереження не приховуємо. Логер отримує `Exception` окремим параметром, не рядком.
* Залежності `IEventRepository`, `IClock`, `IResultRanking`, `ILogger<EventService>` впроваджуються ззовні, що дозволяє тести з дублерами.

## 5. Обґрунтовані винятки аналізаторів

Вимкнені правила **не можна приховувати**. Повний перелік із поясненням міститься поряд із параметром у `.editorconfig`.

* `SA1633`: навчальні файли не мають обов’язкового корпоративного copyright-заголовка.
* `SA1600`: документація публічного API перевіряється через CS1591; уникаємо дублювання загальних summary.
* `SA1402`, `SA1649`: маленькі пов’язані record / інтерфейси можуть бути згруповані у спільному файлі.
* `CA1707` у тестах: xUnit-імена `Method_Situation_Expected` за методичкою ЛР №7.
* `CA1305` у legacy-модулі ЛР №2: культурозалежний формат зберігаємо, щоб під час лабораторного рефакторингу не змінити зафіксований вивід; це зафіксований технічний борг.
* `CA1859` для console-композиції: залишено інтерфейсні залежності для ін’єкції.
* `SA1101`: стиль без зайвого `this.` відповідно до чинного стандарту.

Окремі винятки обмежені конкретною папкою (`labs/lab02`, `SportEvents.Tests`) і не поширюються на весь код без причини.

## 6. Git та перевірка перед здачею

Гілки для окремих лабораторних і PR, невеликі змістовні коміти, жодних `bin` або `obj` у Git. Перед злиттям: виконати збірку, тести, перевірку форматування, порівняти контрольний вивід для рефакторингу та переглянути `git diff`.

Цей файл описує **дійсні правила поточної версії**, а не доводить, що кожний історичний етап лабораторних був виконаний саме цього дня. Використання ChatGPT і Remote Desktop Commander зазначається в навчальних звітах.
