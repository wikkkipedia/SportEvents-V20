## 1. Сфера дії, рівні обов’язковості, глосарій

Цей стандарт застосовують до `SportEvents.Core`, `SportEvents.Console` та `SportEvents.Tests`. Не поширюють на автозгенеровані файли в `obj/bin` і тимчасовий експериментальний код поза основною гілкою. Власник стандарту — автор проєкту; діє з 24.10.2026. Стандарт читається як договір команди, а не лише як оформлення звіту.

**Рівні:** ОБОВ’ЯЗКОВО — помилку потрібно усунути до злиття; РЕКОМЕНДОВАНО — допустимий відступ із поясненням; ДОПУСКАЄТЬСЯ — можна застосовувати обидва стилі; ЗАБОРОНЕНО — не допускають до main. Коди правил: N (іменування), F (формат), C (коментарі), D (типи), X (спортивний домен), S (складність), A (аналіз). Кожен рядок нижче містить формулювання, рівень, обґрунтування, приклад дотримання та перевірку.

Після виправлення на блок із `{ ... }` повторіть збірку. У наданому середовищі немає SDK .NET, тому жодного фальшивого скриншота «зелена збірка» сюди не вставлено.

## Приклади «погано / добре»

### Приклад 1. N-група

ПОГАНО: `class sportevents { }`

ДОБРЕ: `class SportsEvent { }`

Клас PascalCase, назва описує сутність.

### Приклад 2. N-група

ПОГАНО: `interface EventRepo { }`

ДОБРЕ: `interface IEventRepository { }`

Інтерфейс впізнається за I.

### Приклад 3. N-група

ПОГАНО: `void calc() { }`

ДОБРЕ: `void RecordResult() { }`

Метод називає дію.

### Приклад 4. N-група

ПОГАНО: `private int number;`

ДОБРЕ: `private readonly int _eventId;`

Поле відрізняється від параметра.

### Приклад 5. N-група

ПОГАНО: `int t = 120;`

ДОБРЕ: `TimeSpan elapsed = TimeSpan.FromSeconds(120);`

Не плутаються тип та одиниці виміру.

### Приклад 6. N-група

ПОГАНО: `string EventSt = "Open";`

ДОБРЕ: `EventStatus status = EventStatus.Open;`

Enum не допускає друкарських помилок у стані.

### Приклад 7. N-група

ПОГАНО: `List<Participant> person;`

ДОБРЕ: `List<Participant> participants;`

Множина у назві колекції.

### Приклад 8. N-група

ПОГАНО: `bool Flag;`

ДОБРЕ: `bool IsFinished;`

Логічне ім’я відповідає на питання.

### Приклад 9. N-група

ПОГАНО: `void SaveAndPrint()`

ДОБРЕ: `void Save(); void Print();`

Одна функція — одна дія.

### Приклад 10. N-група

ПОГАНО: `void Result2()`

ДОБРЕ: `void GenerateProtocol()`

Прибрано беззмістовну цифру.

### Приклад 11. F-група

ПОГАНО: `if (open) Register();`

ДОБРЕ: `if (open) { Register(); }`

Дужки захищають від помилки при додаванні другого рядка.

### Приклад 12. F-група

ПОГАНО: `namespace SportEvents.Core { class X {} }`

ДОБРЕ: `namespace SportEvents.Core;`

File-scoped зменшує вкладеність.

### Приклад 13. C-група

ПОГАНО: `// цикл по списку; foreach (...) ...`

ДОБРЕ: `foreach (var result in results) ...`

Коментар не повторює очевидне.

### Приклад 14. C-група

ПОГАНО: `// Старий метод більше не потрібний ...`

ДОБРЕ: `/// <summary>Створює протокол за часом.</summary>`

Документація має бути актуальною.

### Приклад 15. D-група

ПОГАНО: `double seconds = 45.123;`

ДОБРЕ: `TimeSpan elapsed = TimeSpan.FromMilliseconds(45123);`

Використано тип тривалості, а не дробове число.

### Приклад 16. D-група

ПОГАНО: `DateTime startDate;`

ДОБРЕ: `DateOnly eventDate;`

Для дати без часу не потрібен DateTime.

### Приклад 17. D-група

ПОГАНО: `int status = 2;`

ДОБРЕ: `EventStatus status = EventStatus.Open;`

Невідомі стани зникають.

### Приклад 18. X-група

ПОГАНО: `result.Elapsed.ToString()`

ДОБРЕ: `result.Elapsed.ToString(@"hh\:mm\:ss\.fff")`

У протоколі єдина точність.

### Приклад 19. S-група

ПОГАНО: `if (data != null) { if (data.Events != null) {...} }`

ДОБРЕ: `ArgumentNullException.ThrowIfNull(data);`

Сторожова перевірка скорочує вкладеність.

### Приклад 20. S-група

ПОГАНО: `if (status == 1) ... else if (status == 2) ...`

ДОБРЕ: `return status switch { ... };`

Явне зіставлення статусів легше розширювати.

### Приклад 21. S-група

ПОГАНО: `if (isOpen == true) {...}`

ДОБРЕ: `if (isOpen) {...}`

Прибрано зайве порівняння.

### Як змінити стандарт
1. Розробник відкриває пропозицію в Git із номером правила, текстом, прикладами «до/після» та очікуваною вигодою.
2. У пропозиції показують аналізатор або чекліст, яким правило перевірятимуть, і вартість переходу.
3. Власник разом з автором зміни порівнює вигоду та ризик, рішення записує в `docs/standard-decisions.md`.
4. Нове правило отримує ID та версію за SemVer; суворіші несумісні правила підвищують major.
5. Зміна вноситься разом з `.editorconfig`, прикладами та тестами, якщо вони потрібні.
6. Старі файли приводяться поступово за правилом бойскаута, протягом наступних двох навчальних тижнів.
7. Якщо правило виявилося шкідливим, відкривають окрему пропозицію на скасування з поясненням, а не просто вимикають аналізатор.

### Журнал рішень стандарту
**STD-01 (24.10.2026).** Контекст: час можна зберігати числом секунд або TimeSpan. Рішення: використовувати TimeSpan для SportEvents. Наслідки: менше плутанини одиниць, потрібен єдиний шаблон виводу.

**STD-02 (24.10.2026).** Контекст: не всі сторонні StyleCop-правила корисні для навчального рішення. Рішення: центрально придушити SA1633 і SA1200 з явними причинами. Наслідки: відсутні зайві вимоги до copyright/позиції using; інші правила залишаються доступними для перевірки.
